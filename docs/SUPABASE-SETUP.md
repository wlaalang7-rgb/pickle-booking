# Supabase setup

The customer booking form and staff dashboard share a Supabase Postgres database. The public site can create pending requests; only signed-in staff can read, change, or delete them. Successful customer booking submissions are limited to five per hour and ten per 24 hours per normalized email address, and ten per hour and thirty per 24 hours per IP address. IPs are stored as keyed hashes in a private schema, not as raw addresses.

## Connect a Supabase project

1. Create a Supabase project.
2. In **Project Settings → API**, copy the **Project URL** and the public **anon** key into `public/js/supabase-config.js`.
   Never use a `service_role` key in this website. Browser code and its anon key are public.
3. In the Supabase **SQL Editor**, run all of `supabase/schema.sql`. This script adds the email, cancellation-token-hash, discount-amount, and booking-group columns to an existing bookings table, enables pending, confirmed, and cancelled statuses, converts existing Paid bookings to Confirmed, adds separate day/night rates to each court, creates the all-court time-block, promo-code, promo-redemption, and private booking-rate-limit tables, installs the booking, cancellation, availability, public-calendar, court-management, date-block, and promo-code functions, and prevents overlapping active bookings for a court or a blocked time range. Existing court rates are copied to both day and night rates during migration, so set the desired separate prices in the staff dashboard after applying the schema. The night rate applies to bookings starting at or after 5 PM; a booking uses one rate for all its hours, based on its start time. It also creates the public `court-images` Storage bucket with a 5 MB limit for JPG, PNG, and WebP files; only signed-in users can upload or delete court photos. Existing court labels are migrated to stable court names; recorded booking totals are not changed. Re-run the latest schema after updating the site to enable image uploads, court deletion, renaming, day/night rate management, timed maintenance/closure blocks, promo-code management and limits, and shared availability for staff-created bookings.
4. In **Authentication → Providers / Sign In**, disable public sign-ups. Create staff users yourself in **Authentication → Users** with the intended staff email and password. Any account allowed to sign in can administer bookings, so do not enable public registration.
5. Serve the site from an HTTP(S) origin (not by opening `index.html` directly). Add that origin to Supabase's allowed site/redirect URLs if required by the project's Auth settings.
6. Submit a test booking from the public form, then open `/admin.html` and sign in with the staff account.

The database uses row-level security: anonymous visitors can read current court rates, submit pending booking requests, check active promo codes, and call restricted functions to cancel their own request or retrieve confirmed booking dates, times, courts, and maintenance/closure windows for the public availability calendar. Visitors and staff can select multiple courts for the same date, start time, and duration; each court is saved as its own booking under one shared request, so availability remains correct and the full request can be cancelled together. Staff can select a date in the booking calendar and block a specific time range across all courts, choose maintenance or club closure, and enter a suggested or custom reason; the all-day option blocks the full date. Individual blocks can be removed from that date's calendar dialog. A time range overlapping pending or confirmed bookings cannot be blocked until those bookings are moved or cancelled. Both customer and staff booking flows disable booking options that overlap a block, and the database rejects overlapping bookings or blocks even if a request bypasses the website or races with a new block. Staff can read and edit day/night court rates, add courts, rename courts (including updating existing booking references in one transaction), create, list, update, and delete booking requests, manage statuses as pending, confirmed, or cancelled, and create, edit, disable, or delete promo codes. A promo discount is applied once to the combined multi-court total. A database trigger prevents overlapping pending or confirmed bookings for the same court and date, including simultaneous requests from multiple visitors or staff. Anonymous visitors cannot read customer details or insert directly into the bookings table. Only authenticated users can access customer booking details.

If the site reports that `create_customer_booking`, `create_admin_booking`, `cancel_customer_booking`, `list_public_bookings`, `list_booking_date_blocks`, `create_booking_date_block`, `delete_booking_date_block`, `update_court_rate`, `add_court`, `rename_court`, `save_court_settings`, `delete_court`, the `court_rates.day_rate`, `court_rates.night_rate`, or `bookings.booking_group_id` column, or the `court_rates` table cannot be found, run the updated `supabase/schema.sql` in the SQL Editor. Public booking stays disabled until current rates and blocked-time availability can be loaded. If the database objects were just added but PostgREST cannot find them, run `NOTIFY pgrst, 'reload schema';` in the SQL Editor.

If the booking form reports that the `email` column is missing, rerun the updated `supabase/schema.sql` in the SQL Editor. If the column exists but the error persists, refresh PostgREST's schema cache by running `NOTIFY pgrst, 'reload schema';` in the SQL Editor, then retry after the database changes are visible.

If the admin page reports **permission denied for table bookings** when creating a booking, the live database is missing the staff insert grant or row-level security policy. Run the latest `supabase/schema.sql` in the Supabase SQL Editor while signed in as the project owner, then sign out and back in to the admin page.

In the staff dashboard, open **Promo codes** and select **Generate code** to create a secure random code. Discounts can be 1–99% or a fixed ₱1–₱100,000 amount; the final estimate never falls below ₱1. Staff can optionally set an expiration in Philippine time and a maximum number of redemptions, and can disable or delete a code. Each code can be redeemed once per email address. A redemption counts when a booking request is successfully saved, even if staff later cancels that booking. The database enforces expiry, remaining uses, one-use-per-customer, and the final total transactionally, including concurrent requests. Existing matching promo bookings are included in redemption counts when the schema is applied or a code is created. The saved booking total and discount amount are retained for staff review and exports.

If promo-code management or validation reports that `promo_codes`, `promo_code_redemptions`, `list_promo_codes`, `create_promo_code`, `save_promo_code`, `delete_promo_code`, or `validate_promo_code` cannot be found, run the latest `supabase/schema.sql` in the SQL Editor. If the new functions are not visible immediately, run `NOTIFY pgrst, 'reload schema';`.

The latest schema no longer uses a **Paid** booking status. Running `supabase/schema.sql` converts existing Paid bookings to **Confirmed** and restricts future statuses to pending, confirmed, or cancelled. The old payment status is not retained separately; record payment details outside the status field if they need to be tracked. From **Courts & rates** in the staff dashboard, staff can change an existing court's name, day rate, night rate, and photo together with one **Save changes** action, upload a JPG, PNG, or WebP photo up to 5 MB, and delete courts that have no booking history. Night pricing begins at 5 PM and is chosen from the booking start time. Uploaded images display with the same public card dimensions and crop. Courts with booking history and the final remaining court cannot be deleted. Court names must be 2–60 characters; each hourly rate must be ₱1–₱100,000, and names are unique regardless of letter case. Existing court changes save atomically; renaming updates the public court cards, booking selector, calendar availability, and dashboard analytics, while existing booking totals remain unchanged. Rate changes apply to new requests, while existing bookings retain their stored estimated totals.

While staff are signed in, the admin page automatically checks for database changes every five seconds and updates its list without a page reload. It checks again when the admin tab becomes visible. The dashboard also has a manual **Refresh now** button. The admin sidebar separates the overview, bookings list, and court-rate editor. The overview shows daily, weekly, monthly, and yearly estimated revenue from bookings marked confirmed, grouped by booking date; booking counts by period; monthly bookings per court; weekly occupancy based on the current court count and 7 AM–10 PM operating hours; booking status counts; and average estimated value for non-cancelled bookings. Its revenue chart shows confirmed booking estimates by scheduled court date and extends its daily, weekly, or monthly timeline to include upcoming confirmed bookings; the booking-activity chart can show weekly (7 days), monthly (30 days), or yearly (12 months) totals. The booking list can be exported as CSV or Excel (`.xlsx`).

The booking RPC reads the client IP from Supabase's forwarded request headers and enforces the per-IP limit above in addition to the per-email limit. Shared networks can reach the same limit, and IP limits cannot stop bots that rotate networks; add Turnstile with server-side validation before exposing the site to significant abuse. Staff confirmation is still required to reserve a slot.
